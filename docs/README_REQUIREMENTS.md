# Требования к README

Собрано из двух источников:
- `Инструкция_для_участников_HackAlem_AI (1).pdf` (корень репо) — общие требования хакатона;
- `task/HackAlem AI_ Граф денег_….pdf` — ТЗ кейса, разделы 7, 9, 10.

## 1. Общие (инструкция участника, п. 7)

README должен содержать:
- [ ] что делает проект;
- [ ] что реализовано;
- [ ] используемые технологии и архитектуру;
- [ ] порядок установки и запуска;
- [ ] пример проверки;
- [ ] используемые данные и внешние сервисы;
- [ ] известные ограничения;
- [ ] ссылку на развёрнутую версию, если она есть.

Также из инструкции:
- не публиковать API-ключи в GitHub;
- итоговый код — в GitHub-репозитории команды, выданном платформой;
- решение сдаётся на странице треков → «Сдать решение» (название + описание), обновлять можно до дедлайна.

## 2. Специфичное для кейса (ТЗ)

README (артефакт обязателен):
- [ ] **как запустить — одна команда**; жюри запускает её на чистой машине, пайплайн отрабатывает < 5 минут и создаёт 3 файла;
- [ ] **описание критериев ролей и порогов** — для каждой роли формальное правило или метрика с порогом (must have 3: жюри называет 3 gid, команда за минуту объясняет роль);
- [ ] **что на выходе** — `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` и экран просмотра;
- [ ] **ограничения подхода**;
- [ ] **раздел про масштабирование** — что изменится при росте графа до ~1 млн узлов (текстом, реализация не нужна);
- [ ] если используются ненаправленные методы (например, кластеризация Louvain) — оговорить явно;
- [ ] выводы формулируются как гипотезы («признаки консолидации»), не как утверждение о виновности;
- [ ] если есть внешний LLM API — указать; всё остальное работает локально.

Схема выходов (проверяется механически):
- `nodes_roles.csv` — ровно 2 248 строк: `gid, role, role_score (0–1), cluster_id, priority_score (0–1), evidence (≤ 200 символов, с числами)`;
- `clusters.csv` — `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`;
- `top_nodes.csv` — ≥ 20 строк по приоритету: `rank, gid, role, priority_score, why`.

Словарь ролей: `consolidator, transit, distributor, terminal, coordinator, peripheral` (можно расширить, задокументировав).

Прочие артефакты (не README, но сдаются вместе):
- [ ] схема решения — один слайд/диаграмма: данные → метрики → роли → интерфейс;
- [ ] демо 5 минут: живой прогон и разбор 2–3 узлов.

Критерии оценки: соответствие задаче 25 · техническая реализация 25 · **README и воспроизводимость 25** · ценность 15 · потенциал 10.

## 3. Промпт организаторов для генерации README

> Проанализируй текущий проект и создай для него полноценный README.md на русском языке.
>
> README должен быть понятен жюри хакатона и содержать:
> 1. Название проекта
> 2. Краткое описание — какую проблему решает проект и для кого.
> 3. Что реализовано — основные функции и возможности решения.
> 4. Как работает решение — кратко опиши основной пользовательский сценарий от входных данных до результата.
> 5. Технологии — языки, фреймворки, библиотеки, AI-модели, API и внешние сервисы.
> 6. Архитектура проекта — основные компоненты и как они взаимодействуют.
> 7. Установка и запуск — пошаговая инструкция с необходимыми командами.
> 8. Как проверить решение — пример сценария, который может повторить жюри.
> 9. Данные и интеграции — какие источники данных, API или внешние сервисы используются.
> 10. Ограничения — что не реализовано или какие ограничения есть у текущей версии.
> 11. Ссылка на deployed-версию, если она существует.
>
> Используй только информацию, которую можно подтвердить по текущему репозиторию. Не придумывай функции, технологии или результаты, которых в проекте нет. Оформи README аккуратно в Markdown.

Итоговый README = 11 пунктов промпта + разделы из §2 (критерии ролей и порогов, выходы, масштабирование).
