# Правила ролей, приоритета и кластеров (v3)

Документ — основа для защиты перед жюри (must-have 3: «жюри называет 3 gid — команда за минуту объясняет роль»).
Каждый порог имеет источник: либо ориентир организаторов из ТЗ, либо перцентиль распределения в данных.

## 0. Метрики узла (считаются из edges/transactions, только внутри графа)

| Метрика | Смысл |
|---|---|
| `in_deg`, `out_deg` | от скольких разных клиентов получил / скольким разным отправил |
| `in_kzt`, `out_kzt` | получил / отправил, ₸ (только видимые внутри графа переводы) |
| `in_tx`, `out_tx` | число переводов |
| `pass_through` | `out_kzt / in_kzt` — доля полученного, ушедшая дальше (NaN если вход 0) |
| `seed_share`, `seed_money_in` | модель «окрашенных денег»: доля и сумма средств, предположительно пришедших от seed (пропорциональное смешивание, итерация до сходимости; знаменатель `max(in, out)`, невидимый вход считается «чистым» — консервативно) |
| `n_seed_upstream` | сколько разных seed достигают узла по направленным путям ≤ 4 шага |
| `betweenness` | посредничество в направленном графе (без весов) |
| `pagerank` | взвешенный по сумме |
| `in_cycle` | участвует в простом цикле длиной ≤ 5 |
| `fast_out_share` | доля исходящей суммы, ушедшей в течение ≤ 2 дней после входящего перевода |
| `sync_in_events` | число дней, когда ≥ 3 разных плательщиков перевели узлу в один день |
| `truncated` | `depth == 4 and out_deg == 0` — обход обрезан, исходящие не выгружались |
| `no_data` (v3) | `truncated` **или** seed без единого ребра — роль по данным не определить (правило 0); 444 + 19 = 463 узла |
| `max_payer_share` (v3) | доля крупнейшего плательщика во входе: `max(сумма от одного плательщика) / in_kzt` (NaN если вход 0) |
| `nearest_role` (v3, в CSV/JSON) | для peripheral — ближайшая роль из §2 (пусто у «нет данных»); для остальных — сама роль |

У 19 seed без единого ребра `seed_share = 0` и `seed_money_in = 0` (v3): это seed, но его денег в графе нет
(в v2 было `seed_share = 1` «по построению» — артефакт при нулевом входе и выходе).

Распределение в данных (среди узлов с ненулевым значением): `in_deg` p95 = 3, p99 = 6; `out_deg` p70 = 3, p90 = 8, p95 = 16, p99 = 61;
`in_kzt` p50 = 50 тыс., p60 = 80 тыс., p80 = 215 тыс., p90 = 416 тыс., p99 = 1,8 млн ₸.
`n_seed_upstream`: ≥ 2 у 46 % активных узлов, ≥ 3 — у 26 %.

## 1. Каскад ролей (проверяется сверху вниз, первое сработавшее правило даёт роль)

Порядок — от самых редких и информативных ролей к самым массовым, чтобы редкая роль не «съедалась» массовой.

**Пороги v2 — перцентили распределения, а не константы.** Блок `PCT_THRESHOLDS` в `run.py`: для каждого степенного/суммового
порога задан перцентиль, совокупность (узлы с `in_deg > 0` / `out_deg > 0` / обоими) и floor. Итог = `max(перцентиль, floor)`,
перцентиль берётся `method="lower"` (реально наблюдаемое значение). floor = порог v1 — защита от вырожденных распределений.
В `node_metrics.json → _meta.thresholds` пишутся итог (`<ключ>`), перцентиль (`<ключ>_pct`) и значение перцентиля до floor (`<ключ>_pct_value`).

| Порог | Перцентиль | Совокупность | floor | Итог на данных | v1 |
|---|---|---|---|---|---|
| `coord_in_deg`, `cons_in_deg` | p95 `in_deg` | in > 0 | 3 | **3** | 3 |
| `coord_out_deg` | p70 `out_deg` | out > 0 | 3 | **3** | 3 |
| `coord_betw_thr` | p95 `betweenness` | in > 0 и out > 0 | 0 | **0,00116** | p95 (линейная интерполяция) |
| `dist_out_deg` | p95 `out_deg` | out > 0 | 15 | **16** | 15 |
| `cons_in_kzt`, `term_in_kzt` | p80 `in_kzt` | in > 0 | 200 000 | **215 000** | 200 000 |
| `tr_in_kzt` | p60 `in_kzt` | in > 0 | 100 000 | **100 000** (p60 = 80 222 < floor) | 100 000 |

Фиксированные (доли и счётчики из ТЗ, от распределения не зависят): `pass_through` 0,3 / 0,8–1,2, `dist_ratio` 3,
`coord_seed_up` 3, `tr_fast_min` 0,5, `weak_seed_share` 0,1, `cons_max_payer` 0,8 (v3).

Известные оговорки (в README):
- Для seed вход занижен по устройству выгрузки → правила 4 и 5 к seed не применяются; seed попадают в coordinator/distributor/consolidator/peripheral.
- Узел с крупным входом от 1–2 плательщиков (или от ≥ 3, но с одним доминирующим ≥ 80 %) и `pass_through < 0,3` — это **terminal** (деньги остались), а не consolidator.
- «Отдал больше, чем получил» (`pass_through` > 1,2 — 320 узлов) — невидимый вход извне графа; `pass_through > 1,2` не считается признаком.

## 2. role_score (0–1)

**Смысл:** уверенность в применимости правила, а не вероятность причастности. 0,8 ≠ «80 %»: это «узел далеко за порогами правила».

**Сработавшая роль:** `role_score = 0,5 + 0,5 × mean(запасов)` по числовым условиям правила. Ровно на всех порогах = 0,5; далеко за порогами → 1,0.

| Тип условия | Запас |
|---|---|
| `x ≥ порог` | `clip((x − порог) / порог, 0, 1)` |
| `x < порог` | `clip((порог − x) / порог, 0, 1)` |
| коридор `lo ≤ x ≤ hi` (transit, 0,8–1,2) | `clip(1 − |x − центр| / полуширина, 0, 1)`, центр = (lo + hi)/2 = 1,0, полуширина = (hi − lo)/2 = 0,2 |

Состав запасов по ролям (логические условия — `depth ∈ {1,2,3}`, «не seed», `in_deg ≥ 1`, `out_deg ≥ 1` — в среднее не входят, они либо выполнены, либо роль не назначена):

| Роль | Запасы в среднем |
|---|---|
| coordinator | `in_deg ≥ 3`, `out_deg ≥ 3`, `betweenness ≥ 0,00116`, `n_seed_upstream ≥ 3` (условие «связь с seed» — ИЛИ; запас считается только по `n_seed_upstream`, даже если сработал цикл: тогда он 0) |
| consolidator | `in_deg ≥ 3`, `pass_through < 0,3`, `in_kzt ≥ 215 тыс.`, `max_payer_share < 0,8` |
| distributor | `out_deg ≥ 16`, `out_deg ≥ 3 × in_deg` (при `in_deg = 0` запас 1) |
| transit | коридор `pass_through` 0,8–1,2, `in_kzt ≥ 100 тыс.`, `fast_out_share ≥ 0,5` |
| terminal | `pass_through < 0,3` (при out = 0 → пропуск 0, запас 1), `in_kzt ≥ 215 тыс.` |

Пример (100000004015047100, consolidator): запасы `in_deg` 9 → 1; `pass_through` 0,0753 → (0,3 − 0,0753)/0,3 = 0,749;
`in_kzt` 919 104 → 1; `max_payer_share` 0,2877 → (0,8 − 0,2877)/0,8 = 0,640; mean = 0,847 → `role_score` = 0,924 (в выгрузке 0,9237).

**peripheral:**
- «нет данных» (правило 0): 1,0 — уверенность в том, что данных нет, а не в том, что узел экономически периферийный;
- иначе `1 − 0,6 × доля выполненных условий ближайшей роли`. Доля = выполненные / все условия правила (включая логические):
  coordinator 4, consolidator 4, distributor 2, transit 6, terminal 4 условия. **Ближайшая роль** = первая по каскаду роль
  с максимальной долей выполненных условий; пишется в `nearest_role`. Чем ближе узел к какой-то роли, тем ниже уверенность в «периферии».
  Пример: 100000003736419100 — `nearest_role = transit`, выполнено 4 из 6 → 1 − 0,6 × 4/6 = 0,60.

## 3. priority_score (0–1) — «кого смотреть первым»

Четыре независимые семьи сигналов (по анализу корреляций: оборот и «красные деньги» коррелируют слабо, ρ = 0,39):

**Приоритет = структура × связь с делом** (v3).

```
base = mean( pct(seed_money_in), pct(n_seed_upstream), pct(in_kzt), pct(betweenness) )
priority = base × role_weight × (0,7 если weak_seed_link, иначе 1)
role_weight: coordinator 1,0 · consolidator 0,9 · distributor 0,7 · transit 0,6 · terminal 0,5 · peripheral 0,2
             · «нет данных» (no_data) 0,5
```
- **«Нет данных» — 0,5, а не 0,2 (v3).** Обрезанный узел с крупным входом «красных» денег — первый кандидат на запрос
  исходящих переводов: роль неизвестна, а не «периферийна». Вес как у terminal — нижняя граница того, чем узел может оказаться.
  На данных лучший из 463 таких узлов — на 161-м месте (seed-денег на входе у обрезанных мало), в топ-30 их нет.
- **Слабая связь с делом — × 0,7 (v3)** (`WEAK_SEED_PRIORITY_MULT` в `run.py`, 1,0 — отключить). Структурный паттерн без денег
  от известных участников (магазин, работодатель) опускается ниже узлов с тем же паттерном и seed-деньгами.
  На данных: из топ-10 v2 ушли 6 координаторов с `seed_share` 0,1–2,8 % (выпали и из топ-30); в топ-30 v3 нет ни одного узла с `weak_seed_link`
  (23 consolidator, 7 coordinator).
`pct` — перцентильный ранг среди всех 2 248 узлов. Для seed вместо `pct(in_kzt)` берётся `pct(out_kzt)` (вход занижен).
Обоснование: оборот сам по себе — плохой критерий (77 из топ-100 по обороту имеют < 10 % «красных» денег);
«красные деньги» и число seed выше по потоку измеряют связь с известными участниками, `in_kzt` — масштаб, `betweenness` — структурную роль.

## 4. Кластеры

Louvain на неориентированной проекции (вес ребра = сумма переводов в обе стороны), `seed=42`.
Оговорки: метод не видит направление денег (направление интерпретируется внутри кластера — кто собирает, кто раздаёт);
разбиение чувствительно к запуску (ARI между запусками 0,90 при весе по сумме — самый стабильный из проверенных; при log-весе 0,68).
Кластер = сообщество Louvain; изолированные узлы получают свой cluster_id.
Гипотеза кластера строится по составу: доля seed, преобладающие роли, крупнейший узел, внутренний оборот.

## 5. Evidence (≤ 200 символов, с числами)

Формат: `<роль>: <правило>; факт: <числа>`. Пороги в тексте правила подставляются из разрешённых значений (не хардкод).
Пример: `consolidator: ≥3 плат., пропуск <0,3, вход ≥215 тыс., макс. плат. <80%; факт: 9 плат., 919 104 ₸, пропуск 0,08, макс. плат. 29%, seed-денег 64%`.
Coordinator: порог посредничества печатается числом — `посредн. ≥0,00116 (p95)` (из `_meta.thresholds.coord_betw_thr`; минимум у 24 coordinator — 0,00131).

**Округление (v3).** Значение рядом с порогом печатается с доп. знаком, чтобы строка не противоречила правилу
(`pass_through` 0,2988 при `<0,3` → «0,299», а не «0,30»). Проценты: сначала округление до 4 знаков, как в CSV, затем до целого
half-up (0,875 → 88 %), одинаково в evidence, why и метриках.

**Слабая связь с делом (v2).** Если роль — coordinator / consolidator / distributor / terminal, а `seed_share < 0,1`,
фрагмент «seed-денег X%» заменяется на `; связь с seed слабая (X%), возможен легальный контрагент`, а в `node_metrics.json`
у узла `weak_seed_link = true`. Смысл: структурный паттерн есть (магазин, работодатель, арендодатель тоже «собирают от многих»),
но деньги в узле почти не прослеживаются до известных участников — гипотеза слабее, нужна ручная проверка.
Роль не меняется, priority умножается на 0,7 (§3).
На данных (v3) флаг получают 199 из 300 узлов «подозрительных» ролей: terminal 135/193, consolidator 33/63, coordinator 17/24, distributor 14/20.
У координаторов это в основном узлы с `out_kzt ≫ in_kzt` (невидимый вход извне графа).
Для «нет данных»: `нет данных: колено 4, данные обрезаны: запросить исходящие переводы; вход 50 000 ₸ от 1 плат., seed-денег 1%`;
для seed без рёбер: `нет данных: seed без переводов ≥5 000 ₸ в июле; 0 вход., 0 исход.`

## 6. Формулировки

Все выводы — гипотезы для проверки («признаки консолидации»), не утверждения о причастности.
