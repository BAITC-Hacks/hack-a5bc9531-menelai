# Синтетические данные Moneylai — спецификация (пре-регистрация)

Зафиксировано 23.09.2026 до генерации. Отчёт сверяется с этим документом, методология задним числом не меняется.

## Цель

Два синтетических датасета в **той же схеме**, что `task/data/` (`nodes.parquet`, `edges.parquet`, `transactions.parquet`),
но с **другими участниками, операциями и объёмами**. Данные должны повторять основные свойства реальных
транзакций и ролей, но не копировать их: генераторы **не видят** `task/data/`, `out/`, `pipeline/` и не подгоняются
под распределения реальной выборки. Сравнение с реальными данными делается только после генерации, как проверка.

## Что генераторы знают (публичный бриф — §Бриф ниже)

Только то, что есть в тексте ТЗ и README датасета: словарь ролей, процесс сбора (81 seed, исходящие, 4 колена,
≥ 5 000 ₸, внутрибанковские, июль 2026), итоговые цифры по коленам, заметка организаторов (8–24 плательщика,
веер 60–116, 72 узла с пропуском 0,8–1,2, 16 компонент) и объявленные ловушки данных. Никаких квантилей сумм,
распределений степеней, дат и т. п.

## Два метода

| | **A — «ИИ пишет журнал»** | **B — стохастическая агентная модель** |
|---|---|---|
| Кто генерирует | несколько независимых LLM-агентов, каждый вручную выдумывает свой кусок мира: конкретных участников и конкретные операции (кто, кому, когда, сколько, зачем) | один Python-генератор (`B_abm/gen.py`), архетипы и поведение заданы кодом, параметры случайны в широких диапазонах, RNG с фиксированным seed (иначе сам датасет не воспроизводим) |
| Разнообразие | от разных авторов и тем: каждая ячейка сети придумана отдельно | от случайности внутри архетипов |
| Масштаб | ограничен объёмом ручного письма | любой |
| Риск | однообразие LLM (круглые суммы, «идеальные» паттерны), ошибки учёта | «слишком чистые» распределения, закладка паттернов прямо под правила |

Оба метода производят **полный мир** (`world_tx`: все переводы, включая входящие извне, мелкие < 5 000 ₸,
межбанковские, июньские/августовские) и **разметку участников**. Датасет получается только через общий обход `crawl.py`.

## Общий обход `crawl.py` (процесс сбора организаторов, одинаковый для A и B)

1. Мир: `world_tx(src, dst, date, amount, channel ∈ {intra, inter})`, `actors(handle, functional_role, involvement, is_known, archetype, note)`.
2. Фильтр наблюдаемости: `channel == intra`, `amount ≥ 5000`, `date ∈ [2026-07-01, 2026-07-31]`, `src ≠ dst`.
3. Seed = `is_known == True`. BFS только по исходящим отфильтрованным переводам: `depth` узла = минимальное колено.
   Выгружаются **все** исходящие переводы узлов колен 0–3 (в том числе уже встреченным узлам, в том числе seed);
   у узлов 4-го колена исходящие не выгружаются. `depth` ребра = `depth(src) + 1`.
4. Seed без исходящих ≥ 5 000 ₸ остаются в `nodes` (как у организаторов: часть seed без рёбер, часть только получатели).
5. gid: `10**17 + k*1000 + 100`, `k` случайно в [10 000, 9 000 000) (формат реальных gid), без пересечений с реальными gid.
6. Выход: `data/{nodes,edges,transactions}.parquet` с теми же dtype (`gid int64`, `depth int64`, `is_seed bool`;
   `edges.depth int8`, `n_tx int64`; `date` — `datetime.date`), плюс `ground_truth.csv`
   (`gid, functional_role, involvement, archetype, note`) — только для наблюдаемых узлов.

## Разметка (ground truth)

- `functional_role` — экономическая функция в словаре ТЗ: consolidator / transit / distributor / terminal / coordinator / peripheral.
  Ставится **по замыслу автора** («этот счёт собирает выручку с 12 закладчиков»), а не по метрикам.
- `involvement` — `criminal` / `legit`. Ловушка: легальный магазин функционально consolidator, работодатель — distributor.
- Истинная роль видимого узла может быть не наблюдаема (обрезана 4-м коленом, мелкие переводы, межбанк) — это фича, а не ошибка.

## Проверки (что считается успехом)

1. **Схема и инварианты — 100 %:** dtype как у реальных файлов; `edges` = агрегат `transactions`; все суммы ≥ 5 000,
   даты в июле; нет петель; у 4-го колена нет исходящих; `edges.depth = depth(src)+1`; все gid рёбер есть в `nodes`;
   нет пересечения gid с реальными.
2. **Сходство (`profile.py`, считается кодом для real / A / B):** узлы по коленам, рёбра, транзакции, оборот; доля seed
   без рёбер и seed-только-получателей; квантили суммы перевода и доля круглых сумм; `n_tx` на ребро; распределение
   по дням месяца и дням недели; квантили in/out-степеней и хвосты (узлы с ≥ 8 плательщиками, с веером ≥ 60);
   число узлов с пропуском 0,8–1,2 и > 1,2; слабосвязные компоненты (число, крупнейшая); быстрый вывод (≤ 2 дней);
   циклы ≤ 5. Для распределений — статистика KS против реальных. Цель — «похоже по форме», а не «совпало до узла».
3. **Роли:** у каждой из 6 ролей есть наблюдаемые размеченные примеры обоих типов вовлечённости, где это осмысленно;
   есть аналоги заметки организаторов (много плательщиков, крупный веер, пропускные счета).
4. **Оригинальность:** 0 общих gid с реальными; объёмы отличаются от реальных; генераторы не читали `task/data`.
5. **Ручной аудит:** по 5 случайных размеченных узлов из каждого набора — трассировка по сырым транзакциям:
   видна ли заявленная роль, согласована ли разметка с деньгами.

Вердикт «какой метод лучше» — по пунктам 1–5, с числами. Несходимость фиксируется как находка.

## Бриф для генераторов (единственный вход авторов A и B)

**Контекст.** Банк второго уровня, Казахстан, тенге (₸). Правоохранительные органы передали банку 81 клиента —
нижний уровень сети сбыта наркотиков («курьеры», «закладчики», дропы, получавшие оплату). Банк выгрузил их
исходящие внутрибанковские переводы и дальше на 4 колена. Задача аналитика — восстановить, кто выше: кто собирает
деньги, через кого их прогоняют, кто распоряжается. Вокруг — обычная жизнь: семьи, аренда, зарплаты, магазины,
долги друзьям, такси, коммуналка, мелкий бизнес. Большинство контрагентов в выгрузке — не преступники.

**Роли (функция счёта):**
consolidator — аккумулирует средства от нескольких участников; transit — пропускает средства дальше, не удерживая
(обычно быстро, за 1–2 дня); distributor — веерное распределение на много получателей; terminal — деньги приходят
и остаются (снятие наличных, покупка актива, «кошелёк» бенефициара); coordinator — координирующий узел,
кандидат в организаторы (и собирает, и раздаёт, связывает части сети); peripheral — признаков роли нет.

**Как собиралась выгрузка:** 81 seed; только исходящие переводы; 4 колена; переводы < 5 000 ₸ не попали;
только внутрибанковские; июль 2026. Входящие переводы извне выборки не видны, поэтому у seed вход занижен.
Узлы 4-го колена — без исходящих (обход остановился), это не «сток».

**Цифры реальной выгрузки (ориентир масштаба, не цель):** узлов по коленам 81 / 472 / 462 / 789 / 444 (всего 2 248),
3 119 пар плательщик→получатель, 4 840 переводов, оборот ≈ 366 млн ₸. 19 из 81 seed без переводов ≥ 5 000 ₸,
ещё 12 только получатели. 16 слабосвязных компонент (крупнейшая ~1 900 узлов). Организаторы: есть узлы с входом
от 8–24 разных плательщиков, веерные рассылки на 60–116 получателей, ~70 узлов, пропускающих 0,8–1,2 полученного;
при кластеризации — ~8 сообществ с несколькими seed.

**Чего хотим от синтетики:** правдоподобная жизнь месяца, а не учебник. Разная масштабность ячеек, шум, неидеальные
паттерны (часть денег осела у транзита, сборщик иногда платит за квартиру, курьер платит за такси), легальные
«двойники» преступных паттернов (магазин собирает от многих, работодатель раздаёт веером, семья переводит туда-обратно),
переводы ниже порога и межбанковские (они исчезнут при сборе), даты вне июля. Суммы — реалистичные для Казахстана 2026.
