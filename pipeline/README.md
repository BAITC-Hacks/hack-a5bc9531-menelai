# Пайплайн: роли, кластеры, приоритет

Детерминированный Python-пайплайн кейса «Граф денег». Правила ролей и порогов подробно описаны в [`RULES.md`](RULES.md) (v3), реализация — в [`run.py`](run.py). В расчёте ролей LLM не используется.

## 1. Что делает пайплайн

На входе три файла (`--data`, по умолчанию `task/data/`): `nodes` (клиенты: gid, колено, is_seed), `edges` (направленные рёбра) и `transactions` (переводы с датой), каждый — `.parquet` с колонками из `task/README.md`. В выданной выгрузке это 2 248 клиентов (81 seed, колено 0–4), 3 119 рёбер и 4 840 переводов. Число колен, период и порог суммы не зашиты: последнее колено берётся как `max(depth)`, период — из дат переводов; всё это пишется в `_meta`. Ошибки схемы (нет файла или колонки, `edges ≠ Σ transactions`, src/dst вне `nodes`) печатаются одной строкой `ОШИБКА ВХОДНЫХ ДАННЫХ: …`. По ним пайплайн считает метрики узлов: степени, суммы, коэффициент пропуска, «окрашенные» seed-деньги, посредничество, циклы, быстрый вывод и синхронные входы. Затем каскадом правил назначает каждому узлу одну из 6 ролей, находит кластеры (Louvain) и считает `priority_score` — «кого смотреть первым». На выходе три CSV по схеме ТЗ и `node_metrics.json` для интерфейса. Все выводы — гипотезы («признаки консолидации»), а не утверждения о причастности.

Время прогона `run.py` — **3,3–3,5 с** (печатается в последней строке). Вместе с `uv sync` при прогретом кэше — 4,2 с (macOS, замер 23.09.2026). На чистой машине первый `uv sync` дополнительно скачивает зависимости, версии зафиксированы в `uv.lock`.

## 2. Запуск одной командой

```bash
cd pipeline && uv sync && uv run python run.py
```

Пути по умолчанию: `--data ../task/data --out ../out`, они относительны папки `pipeline/`. Нужны [uv](https://docs.astral.sh/uv/) и Python ≥ 3.12 (`pyproject.toml`); uv при необходимости поставит Python сам. Сеть нужна только для установки зависимостей.

**Без uv:**

```bash
cd pipeline
python3 -m venv .venv && . .venv/bin/activate
pip install "pandas>=2.2" "pyarrow>=16" "networkx>=3.3" "numpy>=1.26" "scipy>=1.13" pytest
python run.py
```

**Как убедиться, что прогон прошёл.** В конце `run.py` выполняет встроенные проверки (`checks()`: строка на каждый gid входа, роли из словаря, скоры в 0–1, evidence ≤ 200 символов, число «обрезанных» узлов и seed без рёбер совпадает между `role_rule` и метриками, согласованность JSON и CSV) и печатает `ПРОВЕРКИ: все assert'ы пройдены`, затем сводку ролей, топ-20 и пороги. В `out/` появятся:

| Файл | Строк (`wc -l`) | Содержимое |
|---|---|---|
| `nodes_roles.csv` | 2 249 = 2 248 + заголовок | 6 колонок |
| `clusters.csv` | 92 = 91 кластер + заголовок | 6 колонок |
| `top_nodes.csv` | 31 = 30 + заголовок | 5 колонок |
| `node_metrics.csv` | 2 249 = 2 248 + заголовок | 35 колонок |

(Числа строк — для выданной выгрузки; на другом входе их столько, сколько узлов и рёбер в нём.)

## 3. Что на выходе

**`nodes_roles.csv`** — строка на каждый из 2 248 узлов, отсортирована по `priority_score`.
- Ровно 6 колонок схемы ТЗ, в этом порядке: `gid, role, role_score, cluster_id, priority_score, evidence`. Других колонок нет.
- Метрики узла и `role_rule` лежат в `node_metrics.csv` (см. ниже).

**`clusters.csv`** — `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis`. Колонка `top_gids` содержит до 5 gid кластера с наибольшим приоритетом через `;`. Гипотеза собирается по составу кластера: самая информативная роль, доля seed, роли, крупнейший узел и внутренний оборот. Кластер 0: «Гипотеза: признаки координирующего ядра… 277 узлов, seed 1; роли: coordinator 10, consolidator 14, …».

**`top_nodes.csv`** — `rank, gid, role, priority_score, why`, топ-30 (ТЗ требует ≥ 20). Колонка `why` раскрывает, почему узел в топе: суммы и число контрагентов, число seed выше по потоку, seed-деньги на входе, циклы, синхронные входы, быстрый вывод, посредничество и кластер. В текущем топ-30: 23 consolidator и 7 coordinator.

**`node_metrics.csv`, `edge_metrics.csv`** — промежуточный слой по контракту `docs/PIPELINE_CONTRACT.md` (ветка `main`), для анализа; сервер читает `node_metrics.json`. В `node_metrics.csv` по одной строке на узел: колонки контракта `gid … cluster_id`, затем метрики правил `n_seed_upstream, fast_out_share, sync_in_events, max_payer_share, no_data, nearest_role` (смысл — в `RULES.md` §0) и `role_rule` — id сработавшего правила: имя роли для ролей 1–5, `peripheral` (ни одно правило не сработало), `no_data_truncated` (колено 4, обход обрезан), `no_data_isolated_seed` (seed без рёбер). `truncated_by_depth` = `truncated` из `RULES.md`, `no_edges` = узел без рёбер, `real_sink` = колено < 4, не seed и `out_deg = 0`. Дополнительно в файле: даты и `active_days` по переводам (узел как отправитель или получатель); `component` — слабосвязная компонента (0 = крупнейшая, дальше по убыванию размера, при равном размере раньше идёт компонента с меньшим gid); `same_day_bursts` — число пар (контрагент, день, направление) с ≥ 2 переводами. `edge_metrics.csv` — строка на ребро из `edges.parquet`: суммы, min/max перевода, даты, `mutual` (есть встречное ребро) и `back_edge` (`dst_depth ≤ src_depth`). Во всех CSV булевы значения пишутся как `true`/`false`, даты — `YYYY-MM-DD`, пустое значение — пустая строка.

**`node_metrics.json`** — данные для интерфейса (их читает `server/src/data/`). По каждому gid (ключ — строка: gid больше 2⁵³ и в float теряет точность) хранятся все метрики выше, а также `role, role_score, priority_score, cluster_id, evidence, weak_seed_link`, до 3 кратчайших циклов (`cycles`), даты синхронных входов (`sync_days`) и топ-5 входящих и исходящих контрагентов (`top_in`, `top_out`). В ключе `_meta` лежат итоговые пороги с перцентилями, веса ролей, число узлов по ролям, описание выгрузки (`max_depth`, `n_by_depth`, `period`, `min_tx_kzt`) и итоги по графу: 3 119 рёбер, 4 840 переводов, 468 циклов длиной ≤ 5, 91 кластер (72 многоузловых), оборот 365 890 012 ₸.

## 4. Критерии ролей и пороги

Роль даёт **каскад**: правила проверяются сверху вниз, срабатывает первое подходящее. Порядок идёт от редких и информативных ролей к массовым, чтобы редкая роль не «съедалась» массовой. Например, узел, который и собирает, и раздаёт, должен стать coordinator раньше, чем подойдёт под consolidator. Степенные и суммовые пороги считаются как перцентили распределения в данных с нижней границей (floor): `max(перцентиль, floor)`, `method="lower"`. Итоговые значения записываются в `_meta.thresholds`.

| # | Роль | Правило (пороги на этих данных) | Откуда порог | Узлов |
|---|---|---|---|---|
| 0 | peripheral, `no_data` | 4-е колено без исходящих (обход обрезан) **или** seed без единого ребра | ТЗ: обрыв на 4-м колене — артефакт выгрузки | 463 (444 + 19) |
| 1 | **coordinator** | `in_deg ≥ 3` и `out_deg ≥ 3` и (цикл ≤ 5 **или** ≥ 3 seed выше по потоку за ≤ 4 шага **или** seed, получающий от seed) и `betweenness ≥ 0,00116` | p95 `in_deg`, p70 `out_deg`, p95 betweenness среди узлов с входом и выходом | 24 |
| 2 | **consolidator** | `in_deg ≥ 3` и `pass_through < 0,3` и `in_kzt ≥ 215 000 ₸` и доля крупнейшего плательщика `< 0,8` | p95 `in_deg`, p80 `in_kzt`; 0,3 и 0,8 — фиксированные доли | 63 |
| 3 | **distributor** | `out_deg ≥ 16` и `out_deg ≥ 3 × in_deg` | p95 `out_deg`; ориентир организаторов — веер на 60–116 получателей | 20 |
| 4 | **transit** | вход и выход ≥ 1, `0,8 ≤ pass_through ≤ 1,2`, `in_kzt ≥ 100 000 ₸`, ≥ 50 % выхода ушло ≤ 2 дней после входа, не seed | коридор 0,8–1,2 — ориентир организаторов; p60 `in_kzt` = 80 222 ниже floor, поэтому действует floor 100 000 | 20 |
| 5 | **terminal** | колено 1–3, `pass_through < 0,3` (или выхода нет), `in_kzt ≥ 215 000 ₸`, не seed | p80 `in_kzt`; без суммового порога роль раздувается до 1 159 узлов | 193 |
| 6 | peripheral | всё остальное: «признаков роли не выявлено» | — | 1 465 |

Всего peripheral 1 928 узлов, из них 463 с `no_data`. У остальных 1 465 в колонке `nearest_role` указана роль, до которой узел «не дотянул»: terminal у 964, transit у 370 и т. д.

**Почему так.** Coordinator должен и собирать, и раздавать, и стоять между частями сети (верхние 5 % по посредничеству). Consolidator — это сбор от нескольких участников с удержанием ≥ 70 %. Если один плательщик дал ≥ 80 % входа, узел считается получателем одного перевода и идёт дальше по каскаду: 4 таких кандидата стали terminal. Transit обязан пропускать деньги быстро: получил и потратил через месяц — это не транзит. Terminal и transit не назначаются seed, потому что вход у seed занижен устройством выгрузки. Полное обоснование каждого порога — в `RULES.md` §1.

**Evidence** (≤ 200 символов, максимум в выгрузке — 192) строится по формату `<роль>: <правило с порогами>; факт: <числа узла>`. Пороги подставляются из рассчитанных значений, а не вписаны в код. Реальные строки из `out/nodes_roles.csv`:

```
100000004015047100  consolidator: ≥3 плат., пропуск <0,3, вход ≥215 тыс., макс. плат. <80%; факт: 9 плат., 919 104 ₸, пропуск 0,08, макс. плат. 29%, seed-денег 64%
100000003684369100  coordinator: ≥3 плат., ≥3 получ., посредн. ≥0,00116 (p95), ≥3 seed/цикл; факт: 24 плат., 62 получ., посредн. 0,00230, цикл, seed выше 6, сам seed
100000008144528100  terminal: колено 1–3, пропуск <0,3, вход ≥215 тыс.; факт: колено 2, вход 1 068 203 ₸ от 5 плат., пропуск 0,00; связь с seed слабая (3%), возможен легальный контрагент
```

Значение рядом с порогом печатается с дополнительным знаком, чтобы строка не противоречила правилу: пропуск 0,2988 при пороге < 0,3 выводится как «0,299», а не «0,30».

## 5. role_score и priority_score

**`role_score`** — уверенность в применимости правила, а не вероятность причастности (`RULES.md` §2).
- Для сработавшей роли: `0,5 + 0,5 × mean(запасов)` по числовым условиям. Запас для `x ≥ порог` равен `clip((x − порог)/порог, 0, 1)`, для `x < порог` — `clip((порог − x)/порог, 0, 1)`; для коридора транзита — `clip(1 − |x − 1,0| / 0,2, 0, 1)`. Узел ровно на порогах получает 0,5, узел далеко за порогами — 1,0.
- Пример, 100000004015047100: запасы 1; 0,749; 1; 0,640 → среднее 0,847 → 0,924. В выгрузке 0,9237.
- peripheral: `1 − 0,6 × доля выполненных условий ближайшей роли`. Например, 100000003736419100 выполнил 4 из 6 условий transit → 0,60. Для `no_data` score = 1,0: это уверенность в том, что данных нет.

**`priority_score`** строится как «структура × связь с делом» (`RULES.md` §3):

```
base     = mean( pct(seed_money_in), pct(n_seed_upstream), pct(in_kzt | у seed — out_kzt), pct(betweenness) )
priority = base × role_weight × (0,7 если weak_seed_link)
role_weight: coordinator 1,0 · consolidator 0,9 · distributor 0,7 · transit 0,6 · terminal 0,5 · peripheral 0,2 · no_data 0,5
```

Здесь `pct` — перцентильный ранг среди 2 248 узлов. Четыре компоненты — независимые семьи сигналов: связь с известными участниками (seed-деньги, число seed выше по потоку), масштаб и структурная роль. Оборот отдельно не годится: 77 из топ-100 по обороту имеют < 10 % seed-денег.
- **× 0,7 при слабой связи с делом** (`weak_seed_link`: роль coordinator, consolidator, distributor или terminal, но seed-денег < 10 %). У такого узла есть структурный паттерн без денег от известных участников: так выглядят магазин или работодатель. Флаг получили 199 из 300 узлов этих ролей. В топ-30 таких узлов нет.
- **0,5 вместо 0,2 для `no_data`**: роль неизвестна, а не периферийна. Обрезанный узел с крупным «красным» входом — кандидат на запрос данных. Лучший из 463 таких узлов стоит на 161-м месте.

## 6. Кластеры

Кластеры ищет Louvain (`networkx.community.louvain_communities`) с `seed=42`. Результат: 91 кластер, из них 72 многоузловых и 19 одиночных (изолированные seed). Id выдаются детерминированно, крупные кластеры первыми.

**Louvain — ненаправленный метод.** Он работает на неориентированной проекции графа, где вес ребра равен сумме переводов в обе стороны. Направление денег кластеры не видят; его интерпретируют роли внутри кластера (кто собирает, кто раздаёт). Кластер — это сообщество наблюдаемых переводов, а не «группа соучастников».

Разбиение зависит от seed алгоритма. По `RULES.md` §4 ARI между запусками составляет 0,90 при весе по сумме (самый стабильный из проверенных вариантов) и 0,68 при log-весе. При подготовке README число перепроверено на 10 seed: попарный ARI при весе по сумме в среднем 0,92 (минимум 0,87), при log-весе в среднем 0,70 (минимум 0,59). Скрипт этого сравнения в репозиторий не сохранён. Внутри одного `seed=42` результат воспроизводится побайтно (§8б).

## 7. Ловушки данных и как они учтены

| Ловушка (проверено кодом на `task/data`) | Что сделано в коде |
|---|---|
| **Обрыв 4-го колена**: 444 узла с `depth = 4` без исходящих — обход закончился, а не «деньги осели» | `truncated`/`no_data` (правило 0): такие узлы не становятся terminal. В evidence — «данные обрезаны: запросить исходящие переводы», вес приоритета 0,5. Обрезанным считается последнее колено выгрузки (`max(depth)`), для выданных данных — 4-е; assert сверяет число таких узлов между `role_rule` и метриками |
| **Только исходящие**: граф собран от seed по исходящим переводам, входящие извне не видны | Все метрики — «внутри графа». `seed_share` использует знаменатель `max(in, out)`: невидимый вход считается «чистым» (консервативно). `pass_through > 1,2` признаком не считается (таких узлов 320) |
| **Вход seed занижен** | seed не бывает transit и terminal. В priority для seed вместо `in_kzt` берётся `out_kzt`. В `why` пишется «Seed-клиент: вход занижен выгрузкой» |
| **Порог выгрузки 5 000 ₸** (минимальный перевод в данных — 5 000) | Мелкие переводы и дробление ниже порога не видны. В коде это не компенсируется, ограничение описано в §9 |
| **31 seed без исходящих**, из них 19 без единого ребра | 19 изолированных seed: `no_data`, `seed_share = 0` (их денег в графе нет), отдельный одиночный кластер, evidence «seed без переводов в выгрузке; 0 вход., 0 исход.». Остальные 12 имеют только входящие и проходят каскад на общих основаниях |
| **16 слабосвязных компонент с рёбрами** (1 877, 270, 17, 13, 6 … узлов) + 19 изолированных seed = 35 | Louvain работает по всему графу; изолированные узлы получают свой `cluster_id`. Посредничество считается по всему графу без нормировки по компоненте (см. §9) |
| **Направленный граф**: ненаправленные метрики стирают движение денег | betweenness, PageRank, циклы и `n_seed_upstream` считаются на `DiGraph`. Ненаправленный только Louvain, это оговорено в §6 |

## 8. Проверка решения

**(а) Синтетический тест.** Команда `cd pipeline && uv run python -m pytest tests -q` выводит `3 passed` примерно за 0,4 с. Вариант с подробной печатью: `uv run python tests/test_synthetic.py`. Тест строит граф из 62 узлов с заложенными паттернами и прогоняет его через тот же `run.compute` и тот же расчёт порогов, что и на реальных данных. Проверяется, что восстановлены:
- coordinator (3 seed → узел → 5 получателей, плюс возвратный цикл) и consolidator (6 плательщиков, отдаёт 5 %);
- distributor (веер на 20 получателей) и transit (получил 300 тыс., на следующий день отдал всё);
- terminal, куда пришли деньги транзита;
- «медленный транзит» (тот же баланс, но вывод через 19 дней) → **не** transit, peripheral;
- узел на 4-м колене с крупным входом → peripheral с `no_data`, а не terminal;
- «магазин» с 6 покупателями без связи с seed → consolidator с `weak_seed_link` и множителем 0,7;
- «сборщик», у которого один плательщик дал 90 % входа → terminal, а не consolidator;
- изолированный seed → `no_data`, `seed_share = 0`.

Отдельно проверяются веса приоритета: 0,5 / 0,2 для `no_data` и 0,7 для слабой связи. Тест проверяет логику каскада, а не калибровку перцентилей: на 62 узлах почти везде действует floor.

**(б) Детерминизм.** Два прогона `run.py` в разные папки дают побайтно одинаковые `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv` и `node_metrics.json`: проверено `cmp`, они совпадают и с закоммиченным `out/`. Источники детерминизма: Louvain `seed=42`, точная betweenness, стабильные сортировки, канонизация циклов.

**(в) Чувствительность к порогам.** Команда `cd pipeline && uv run python sensitivity.py` (~8 с) пишет результат в `out/sensitivity.md`. Каждый из 15 порогов сдвигается на ±20 % по одному, затем все сразу. Признаки узлов не пересчитываются, меняются только роли и приоритет. Критерий зафиксирован до прогона: в каждом одиночном варианте Jaccard топ-20 ≥ 0,80 и роль меняют ≤ 2 % узлов (44). **Итог — неустойчиво по критерию:**
- Топ-20 держится (Jaccard ≥ 0,82) во всех одиночных вариантах, кроме одного: `cons_in_deg` 3 → 4 даёт Jaccard 0,67, четыре consolidator уходят в terminal и выпадают из топа. Целочисленный порог сдвигается минимум на 1, поэтому шаг 3 → 4 равен +33 %, а не +20 %.
- Состав ролей превышает 2 % в одном варианте: `term_in_kzt` 215 000 → 172 000 меняет роль у 49 узлов (топ-20 при этом не меняется). Самые чувствительные пороги — `cons_in_deg` (40 и 32 узла) и `term_in_kzt` (49 и 42).
- Все пороги сразу: мягче — Jaccard 0,67, роль сменили 134 узла; строже — 0,54 и 102.
- Вывод: граница consolidator/terminal — самое хрупкое место правил. Координаторы, дистрибьюторы и транзиты устойчивы: их одиночные сдвиги меняют ≤ 9 узлов.

**(г) Симуляция жюри на LLM.** Скрипты лежат в `eval/`, отчёт — в [`eval/jury_report.md`](eval/jury_report.md), сырые ответы — в `eval/raw/`. Модель `gpt-5.6-sol` (OpenAI) в роли жюри получила правила и выгрузки и сделала три вещи:

## 9. Ограничения подхода

- **Роли действуют только в пределах выгрузки**: один банк, один месяц (июль 2026), переводы ≥ 5 000 ₸, только дата без времени. terminal означает «конечный в пределах видимого»: вывод в другой банк, наличными или в августе не виден, а поступления в конце месяца «оседают» искусственно.
- **Модель «окрашенных денег» — допущение**: деньги смешиваются пропорционально (pro-rata), а невидимый вход считается «чистым». `seed_share` измеряет экспозицию к seed, а не прямую трассировку происхождения средств.
- **Слабая связь с делом у части ролей**: 199 из 300 узлов coordinator, consolidator, distributor и terminal имеют < 10 % seed-денег. Среди terminal таких 135 из 193. Это структурные кандидаты, возможны легальные контрагенты. Приоритет у них снижен, роль не меняется.
- **Coordinator**: `in_cycle` считается по месячному агрегату, без проверки хронологии (B→A мог быть раньше A→B). betweenness не взвешена и не нормирована по компоненте, поэтому «координатором» может стать технический мост выборки. Все 24 координатора находятся в цикле ≤ 5: фактическим фильтром служит цикл, а не число seed.
- **Seed**: из-за заниженного входа seed не бывает transit и terminal, но может стать consolidator (2 узла) и distributor (5 узлов).
- **Transit** сопоставляет вход и выход по окну 0–2 дня, а не попереводно (FIFO), и не отличает возврат тому же плательщику от транзита дальше.
- **Каскад**: роль зависит от порядка правил, по одной роли на узел.
- **Louvain** не учитывает направление, и его разбиение зависит от seed (§6).
- **Пороги откалиброваны под эту выгрузку**: перцентили с floor. Граница consolidator/terminal чувствительна к порогам (§8в).

## 10. Масштабирование до ~1 млн узлов

При текущей плотности (~1,4 ребра на узел) граф вырастет примерно до 1,4 млн рёбер. Линейные части пайплайна масштабируются без изменений или почти без изменений: агрегаты `groupby`, `seed_share` на `np.bincount`, временные признаки на `merge_asof`. Упираются в потолок две вещи — точная betweenness (O(n·m)) и перебор простых циклов. В networkx на 1 млн узлов они практически не считаются. Что менять:

| Узел пайплайна | Сейчас | При ~1 млн узлов |
|---|---|---|
| Хранение и загрузка | pandas + parquet | parquet + DuckDB или polars (lazy, колоночные агрегаты), без загрузки всего в pandas |
| Граф | networkx | igraph или graph-tool (C/C++); для кластера — Spark GraphFrames |
| betweenness | точная, O(n·m) | приближённая сэмплированием k источников (`betweenness_centrality(k=…)` в networkx; в igraph — отсечка длины пути `cutoff`), считать внутри компонент/кластеров |
| Циклы | `simple_cycles`, длина ≤ 5 по всему графу | длина 3–4, только внутри кластеров и только для кандидатов (coordinator/transit) |
| Кластеры | Louvain (networkx) | Leiden в igraph/leidenalg: быстрее и даёт связные сообщества |
| `seed_share` | итерация на плотных numpy-массивах | разреженная матрица переходов `scipy.sparse`, те же итерации (scipy уже в зависимостях) |
| `n_seed_upstream` | BFS от каждого seed | multi-source BFS или разреженные степени матрицы смежности с отсечкой 4 |
| Пересчёт | весь граф заново | инкрементально, по затронутым компонентам и кластерам; признаки хранить в parquet или DuckDB |
| Каскад ролей | `iterrows` по узлам | векторные условия (маски polars/numpy) |

Оценка времени (порядок величины, **не измерено**): сейчас 3,5 с на 2 248 узлах. Линейные этапы на 1 млн узлов займут минуты. Точная betweenness в networkx — часы и сутки, что неприемлемо. Приближённая betweenness в igraph и циклы только внутри кластеров укладываются в десятки минут на одной машине.
